# Issue 39 Public Judge Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** The public, no-account `/judge` page where an evaluator uploads a
fresh synthetic SI and draft BL, watches an honest live check, inspects all
seven field verdicts with a working evidence click, downloads the demo
artifacts, and, if the live provider fails, keeps the failed upload with a
retry while a separately labelled `PREPARED FALLBACK` example appears.

**Architecture:** `features/judge/judge-api.ts` is a typed client over the
#30 judge endpoints (it reuses `apiFetch`/`apiJson` from `lib/api.ts`, which
mints the guest API session automatically). `features/judge/JudgeView.tsx`
is a small state machine — `idle`, `checking`, `result`, `failed` — that
composes an upload panel, the existing `ComparisonGrid` and
`EvidenceViewer` from the email detail feature, a failure panel, a prepared
fallback panel, gate summaries, and downloads. The route renders it outside
the operator shell and never requires `/auth`.

**Tech Stack:** React 19, react-router-dom 7, Vitest + Testing Library,
in-house components only.

**Spec:** GitHub issue #39; `docs/TRD.md` "Failure contract";
`docs/DESIGN.md` "Components" (Drop zone), "States", "Accessibility";
research `docs/research/build/judge-upload-ux.md`; the #30 API contract in
`docs/references/api.md` (repeated below).

## Global Constraints

- `/judge` is reachable directly without guest sign-in; it calls
  `ensureGuestSession()` and the API client mints the server session.
- UX: low cognitive load, concise domain language, no internal jargon;
  secondary captions only in the `Tooltip` "i" beside headings; critical
  warnings and actions permanently visible.
- The drop zones name accepted formats (TXT, PDF, DOCX, XLSX) and the size
  ceiling (from `GET /api/judge/policy`) before any upload, and explain a
  rejected file inline in the `state/mismatch/text` treatment — never a
  browser alert.
- While checking: honest progress (plain text plus an elapsed-seconds
  counter in a `role="status"` region); never render a `StatusPill` or a
  fake result skeleton before the result exists.
- Result: all seven field rows with verdicts; clicking a value opens the
  `EvidenceViewer`; for TXT documents it also shows the source line with
  the value highlighted (fetched from the document's `evidence_url`).
- Failure (`state: "FAILED"`): first disclose that the live check failed and
  why (the `failure.message`), keep the uploaded file names and a Retry
  button visible, and only then show the `PREPARED FALLBACK` panel with a
  different prepared pair; never claim the upload succeeded until a retry
  returns `SUCCEEDED`, which removes the failure and the fallback.
- Synthetic-only: a permanent banner "Synthetic data only. Do not upload
  real shipping documents." and a required confirmation checkbox.
- Downloads: submission JSON and synthetic CSV via authenticated API calls
  saved through an object URL; links to `/inbox`,
  `/review?tab=reconciliation`, and the fallback case `/emails/{example_id}`.
- Store the last run id in sessionStorage key `ladinglens-judge-last-run`
  (Reset All clears it) and reload that run on revisit.
- Commands from `apps/web`: `bun run test`, `bun run lint`, `bun run build`.

## API Contract (from #30)

```text
GET  /api/judge/policy  -> {accepted_formats: ["txt","pdf","docx","xlsx"], max_file_bytes, data_policy, confirmation_required}
POST /api/judge/runs    multipart: si_file, draft_bl_file, synthetic_confirmed="true"
                        -> 201 JudgeRun | 422 {error:{code:"upload_rejected"|"synthetic_only", message, details:[{slot, reason}]}}
                        | 409 {error:{code:"session_reset"}}
GET  /api/judge/runs/{run_id} -> JudgeRun
POST /api/judge/runs/{run_id}/retry -> JudgeRun | 409 {error:{code:"already_succeeded"}}
GET  /api/judge/fallback -> PreparedFallback
GET  /api/summary        -> GateSummary
GET  /api/artifacts/submission.json ; GET /api/artifacts/expected-shipments.csv

JudgeRun {run_id, source:"live", state:"SUCCEEDED"|"FAILED", attempt, created_at, completed_at, latency_ms,
          documents:[{document_id, slot:"si_file"|"draft_bl_file", file_name, detected_format, byte_size,
                      role:"SI"|"DRAFT_BL"|"OTHER"|null, evidence_url}],
          outcome: {category, status, review_reason, has_defect, defect_fields} | null,
          field_verdicts: [{field, si, draft_bl, verdict:"MATCH"|"MISMATCH"|"REVIEW", semantic_probability, reason}],
          diagnostics: [{reason, detail, document_role}],
          failure: {code, retryable, message} | null}
PreparedFallback {label:"PREPARED FALLBACK", source:"prepared", example_id, note, documents:[...], outcome, field_verdicts}
GateSummary {seed_version, source, gate1:{received, accounted, by_category}, comparison:{OK, MISMATCH, NEEDS_REVIEW},
             gate2:{shipments, outcomes}}
```

### Task 4: Failure disclosure, retry, and prepared fallback

**Files:** Create
`apps/web/src/features/judge/components/FailurePanel.tsx`,
`apps/web/src/features/judge/components/PreparedFallbackPanel.tsx` (+
tests); modify `JudgeView.tsx`.

**Interfaces:** On `FAILED`: `FailurePanel({ run, onRetry, retrying })`
renders, in order, a `role="alert"` heading "The live check did not
finish", the failure message, the uploaded file names ("Your upload is
kept: {si} and {bl}"), and a primary "Retry live check" button (disabled
while retrying; hidden with the text "This failure cannot be retried; try
again later." when `failure.retryable` is false). Below it,
`PreparedFallbackPanel` loads `getPreparedFallback()` and renders a
visually distinct panel whose heading is the literal label `PREPARED
FALLBACK`, the note "A prepared example, not your upload.", the example's
file names and outcome, and its seven verdict rows. A retry that returns
`SUCCEEDED` switches to the `result` state and removes both panels; a retry
that fails again keeps them and updates the message.

- [ ] Steps: failing tests (the alert appears before the fallback in DOM
  order; the fallback heading reads `PREPARED FALLBACK` and never the word
  "Your result"; the upload's file names stay visible; retry success
  removes the fallback; non-retryable failure hides the button), implement,
  test, lint, commit —
  `feat(web): keep failed uploads retryable beside a labelled fallback`.
