# Guest sessions and the public judge API

LadingLens runs as one FastAPI service on Cloud Run, serving a React SPA and
JSON APIs to unauthenticated visitors. This note verifies, against primary
sources, how to isolate anonymous guest sessions, accept and cap `/judge`
uploads, serve private evidence bytes, place long provider calls, and
invalidate in-flight work safely, for GitHub issue #30.

## File uploads: UploadFile, size limits, and multipart parsing

FastAPI offers two ways to receive a file: `bytes`, which reads the whole
body into memory, and `UploadFile`, which wraps a `SpooledTemporaryFile` and
"will work well for large files ... without consuming all the memory"
[FastAPI-Files]. `UploadFile` exposes async `read()`, `seek()`, and
`write()`, so a handler can stream or bound its reads instead of loading
everything at once. Both paths require the `python-multipart` package,
since uploaded files arrive as `multipart/form-data` [FastAPI-Files]. Its
absence from `apps/api/pyproject.toml` and `apps/api/uv.lock` (checked
directly) means it must be added before `/judge` can accept uploads.

Neither Starlette nor Uvicorn imposes a default cap on request-body size.
Starlette's own "limit max request size" discussion stayed open for years
[Starlette-Issue890]. As of Starlette 1.6.0, the exact version pinned in
`apps/api/uv.lock`, `Starlette.__init__` accepts `max_body_size: int | None
= None`, documented as "the default, `None`, does not limit request body
size" [Starlette-Requests]. FastAPI's own `FastAPI()` constructor does not
surface that parameter (checked against FastAPI's `applications.py`
source), so the portable options are Starlette's `RequestBodyLimitMiddleware`,
setting `app.router.max_body_size` directly, or enforcing a running byte
count while looping over `UploadFile.read(chunk)`, raising
`HTTPException(413)` once a cap is crossed. The last works on any
FastAPI/Starlette version with no framework-internal API needed.

Multipart parsing has its own limits, added in Starlette 0.25.0 to close a
field/file-count denial-of-service [GHSA-Starlette]. Reading
`starlette/formparsers.py` on the current `master` branch confirms
`MultiPartParser` defaults to `max_files=1000`, `max_fields=1000`, and
`max_part_size=1024*1024` (1 MiB) for each non-file field's value; file
parts instead spool to temporary storage and are "not limited by
`max_part_size`" [Starlette-Requests] (spool threshold `spool_max_size` is
likewise 1 MiB [Starlette-Src]). File size is therefore bounded only by
`max_body_size` (if set), a manual read-loop cap, or the outer Cloud Run
request limit below, not by `max_part_size`.

[FastAPI-Files]: https://fastapi.tiangolo.com/tutorial/request-files/
[Starlette-Issue890]: https://github.com/Kludex/starlette/issues/890
[Starlette-Requests]: https://starlette.dev/requests/
[GHSA-Starlette]: https://github.com/encode/starlette/security/advisories/GHSA-74m5-2c7w-9w3x
[Starlette-Src]: https://github.com/encode/starlette/blob/master/starlette/formparsers.py

## Anonymous guest session identifiers

OWASP's Session Management Cheat Sheet sets a floor: "Session identifiers
must have at least 64 bits of entropy" generated by "a strong CSPRNG"
[OWASP-Session]. It also mandates strict issuance: "Web applications should
never accept a session ID they have never generated" [OWASP-Session]. The
server mints the identifier, full stop; a client-supplied or client-guessed
ID is a session-fixation risk regardless of how random it looks.

Python's `secrets.token_urlsafe(nbytes)` is the direct fit: a CSPRNG-backed,
base64 URL-safe string at roughly 1.3 characters per byte [Python-Secrets].
Its no-argument default currently draws 32 bytes (256 bits), but the docs
warn `DEFAULT_ENTROPY` is "subject to change at any time" [Python-Secrets],
so an explicit `secrets.token_urlsafe(32)` is the stable choice, 4x OWASP's
64-bit floor. `apps/web/src/lib/guest-session.ts` instead mints the session
ID in the browser today from `Date.now()` and `Math.random()` (read
directly), violating both OWASP rules above; MDN is explicit that
`Math.random()` "does not provide cryptographically secure random numbers
... Use the Web Crypto API instead" [MDN-MathRandom]. The fix is
architectural, not just a better generator: the ID must be issued by the
server, never generated by `Math.random()` or even
`crypto.getRandomValues()` client-side.

For transport, OWASP favors cookies with `Secure`, `HttpOnly`, and
`SameSite=Strict` or `Lax` over URL parameters [OWASP-Session]. But
LadingLens's SPA and API share one origin (`docs/TRD.md`, "Deployment,
security, and observability": one Cloud Run service serves both), so a
custom request header is a simpler alternative. OWASP's CSRF Cheat Sheet
documents "Employing Custom Request Headers for AJAX/API" as a standalone
CSRF defense, because "cookies are not set on cross-origin requests (CORS)
by default," and any cross-origin request carrying a custom header must
first pass a CORS preflight the server controls [OWASP-CSRF]. A header the
SPA reads from `sessionStorage` and attaches to `fetch()` calls has no
ambient-credential CSRF surface: nothing for a third-party page to forge,
since the browser never auto-attaches it. That also sidesteps `SameSite`
nuance, where an unspecified attribute defaults to `Lax` per the current
draft standard, section 5.6.7 [RFC6265bis], and MDN notes `Lax` still ships
on some cross-site POSTs made within two minutes of the cookie being set
[MDN-SameSite]. If a cookie is used instead, pair it with `SameSite=Strict`
and `Secure`, since the SPA never needs it sent on a cross-site navigation.

[OWASP-Session]: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
[Python-Secrets]: https://docs.python.org/3/library/secrets.html
[MDN-MathRandom]: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/random
[OWASP-CSRF]: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
[MDN-SameSite]: https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie

## Serving private evidence bytes

`apps/api/app/storage.py`'s `GcsPrivateObjectStore.read_private()` already
downloads bytes server-side through an authenticated `storage.Client`
(`blob.download_as_bytes()`) rather than issuing a public or signed URL,
consistent with the TRD requirement to "keep source objects private and
deliver evidence through authorized API endpoints, never public bucket
URLs" (`docs/TRD.md`, "Deployment, security, and observability"). Google's
own guidance backs the private-by-default posture: with uniform
bucket-level access, "access to Cloud Storage resources ... is granted
exclusively through IAM" [GCS-UBLA]; objects stay unreachable by the public
unless IAM explicitly grants `allUsers` or `allAuthenticatedUsers`, which
this design never does.

An API route that re-serves those bytes should return `Content-Disposition`
and `X-Content-Type-Options: nosniff`. RFC 6266 defines `Content-Disposition:
attachment; filename=...` to tell the browser to save rather than render the
payload [RFC6266], and warns that a recipient "MUST NOT" be able to write
outside its intended save location, so control characters and `..`
segments in a filename must be stripped [RFC6266]. `X-Content-Type-Options:
nosniff` stops the browser from re-sniffing the MIME type, closing a
stored-XSS path for attacker-controlled uploads served back through the API
[MDN-XCTO]. FastAPI's `Response`/`StreamingResponse` both accept a
`headers: dict` [FastAPI-Response]:

```python
headers = {
    "Content-Disposition": 'attachment; filename="evidence.pdf"',
    "X-Content-Type-Options": "nosniff",
}
return StreamingResponse(chunks, media_type="application/pdf", headers=headers)
```

Cloud Run bounds every request and response: "Maximum HTTP/1 request size:
32 MiB per request ... No limit if using HTTP/2 server," and the same 32
MiB cap applies to responses "if not using `Transfer-Encoding: chunked` or
streaming" [Cloud-Run-Quotas]. `StreamingResponse` avoids that response cap
for larger evidence files. Request timeout defaults to 300 seconds and can
be raised to a maximum of 3600 seconds [Cloud-Run-Timeout].

[GCS-UBLA]: https://cloud.google.com/storage/docs/uniform-bucket-level-access
[RFC6266]: https://www.rfc-editor.org/rfc/rfc6266
[MDN-XCTO]: https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Content-Type-Options
[FastAPI-Response]: https://fastapi.tiangolo.com/advanced/custom-response/
[Cloud-Run-Quotas]: https://cloud.google.com/run/quotas
[Cloud-Run-Timeout]: https://cloud.google.com/run/docs/configuring/request-timeout

## Where a live judge run should execute

FastAPI's `BackgroundTasks` only runs "after returning a response," and the
docs point elsewhere for real work: "If you need to perform heavy background
computation ... you might benefit from using other bigger tools like
Celery" [FastAPI-BG]. That caveat compounds with how Cloud Run bills CPU.
Under the default request-based billing, Google's container-contract page
states, under "CPU": "CPU is allocated when instances are processing
requests"; sustained CPU outside of request handling requires switching the
service to instance-based billing instead [Cloud-Run-Contract]. A
`BackgroundTasks` job or a detached `asyncio.create_task` that keeps calling
Gemini or Jev after the response has already been sent is therefore not
guaranteed CPU to finish on a request-billed instance.

For a synchronous, visible `/judge` result, the safest design is to run the
Gemini and Jev calls inline, awaited inside the request handler, and let the
HTTP response itself carry the result. Cloud Run's request timeout (300s
default, up to 3600s, see above) is the real budget, not any in-process
background mechanism. If the UI instead wants a polling experience, each
poll must itself be a request that performs or resumes the provider work
synchronously and persists partial progress between polls, never a
fire-and-forget task started by an earlier, already-returned request.

[FastAPI-BG]: https://fastapi.tiangolo.com/tutorial/background-tasks/
[Cloud-Run-Contract]: https://cloud.google.com/run/docs/container-contract

## Invalidating in-flight jobs with a generation counter

PostgreSQL's `SELECT ... FOR UPDATE` "causes the rows retrieved ... to be
locked as though for update," blocking concurrent `UPDATE`, `DELETE`, or
another `FOR UPDATE` on the same row "until the current transaction ends"
[PG-Locking]: the primitive for a safe check-then-commit.

LadingLens already implements the pattern this issue needs. `GuestSession`
(`apps/api/app/models.py:60`) carries a `current_generation` counter
(`CHECK (current_generation > 0)`); `Workspace`
(`apps/api/app/models.py:72`) is uniquely keyed on
`(guest_session_id, generation)`. `PersistenceService.reset_guest_namespace`
(`apps/api/app/persistence.py:1246`) takes `SELECT ... FOR UPDATE` on the
caller's `GuestSession` row, increments `current_generation`, and opens a
fresh `Workspace` at the new generation; this is what `POST /api/reset`
should call. Every mutation that must not land against a stale generation
already re-checks it under the same lock:
`PersistenceService._require_active_guest_workspace`
(`apps/api/app/persistence.py:2511`) selects the guest session
`.with_for_update(of=GuestSession)` and requires `Workspace.generation ==
GuestSession.current_generation` before proceeding. A judge run should take
this same dependency: capture `current_generation` when the run starts, and
re-acquire the lock and re-compare immediately before persisting the judge
result, so a reset that lands mid-run makes the late write fail closed
instead of silently attaching a stale result to a reset workspace.

[PG-Locking]: https://www.postgresql.org/docs/current/explicit-locking.html

## Implications for LadingLens

- **Add `python-multipart`** to `apps/api/pyproject.toml`: required for
  `UploadFile`/form parsing and absent from `apps/api/uv.lock` today.
- **Cap `/judge` upload size explicitly**, with a running byte count while
  looping over `UploadFile.read(chunk)` (413 past the cap), rather than
  relying on `max_part_size` (bounds only non-file form fields) or on
  FastAPI surfacing Starlette 1.6.0's `max_body_size`, which it does not.
  Cloud Run's 32 MiB HTTP/1 request ceiling is the outer bound regardless.
- **Mint the guest session ID server-side** with `secrets.token_urlsafe(32)`,
  for example behind a new `POST /api/session`. Stop generating it in
  `apps/web/src/lib/guest-session.ts`: its `Math.random()`/`Date.now()`
  scheme fails OWASP's entropy and server-issuance rules and is exactly
  what MDN warns against.
- **Transport it as a custom header** (for example `X-Guest-Session-Id`,
  matching the existing `X-Request-ID` convention in
  `apps/api/app/observability.py`) rather than a cookie: same-origin SPA
  and API need no cross-site delivery, and a header the SPA must explicitly
  attach has no CSRF surface, simpler than cookie attributes plus a token.
- **Run the Gemini and Jev calls inline inside the `/judge` request**,
  awaited in the handler, not a `BackgroundTasks` job or detached `asyncio`
  task: Cloud Run only guarantees CPU while a request is in flight under
  the default (request-based) billing. If polling is wanted for UX, each
  poll request must itself perform or resume the provider work.
- **Reuse the existing generation/epoch mechanism** for judge runs:
  `POST /api/reset` should call the existing
  `PersistenceService.reset_guest_namespace`; the judge-run write path
  should gate its final commit through the same
  `with_for_update(of=GuestSession)` plus generation-match check already
  used by `_require_active_guest_workspace`, so a reset mid-run fails the
  stale write instead of racing it.
- **Serve evidence via `StreamingResponse`** with `Content-Disposition:
  attachment; filename="..."` and `X-Content-Type-Options: nosniff`,
  sourced only from `GcsPrivateObjectStore.read_private()` (never a public
  or signed GCS URL), consistent with uniform bucket-level access keeping
  the bucket IAM-only.
