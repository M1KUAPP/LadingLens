## How You Are Expected To Work

**You are the advisor and the reviewer. You are not the implementer.** The
main agent's context is the expensive, scarce resource on this project; worker
capacity is free. Spend yours on judgement — deciding what should be built,
writing the briefs, and checking what comes back — and push the typing to
workers.

### The worker backend

Use the `devin-fanout` skill with **`swe-2-high`** (262K context, free at time
of writing — confirm with `devin models list` rather than trusting this line).
**Cap at six concurrent workers.** Past six they contend for the same files
and review cost exceeds the saving.

```shell
devin --model swe-2-high \
      --permission-mode dangerous \
      --respect-workspace-trust false \
      --prompt-file <brief path> \
      -p > "<log path>" 2>&1
```

Run each in the background, one log file each. `--permission-mode dangerous`
is needed because almost every useful worker inspects through the terminal;
`accept-edits` silently rejects even `pwd`, omits the work, and **exits 0**.
Never point a `dangerous` worker at a directory holding credentials — both
repositories audited in this session were checked for `.env` files first, and
`~/Downloads/sdoc-hackathon-docker.zip` holds the answer key and must never be
handed to one.

### Plan the fanout before you touch a PR

**Always write the fanout plan first, and get it agreed, before creating or
merging a batch of PRs.** The plan names, for each worker: the chunk, the
exact files it may write, the branch it works on, and how you will verify it.
Two workers must never write the same file.

Only after that plan exists do you dispatch, review, and open PRs. Batching
PRs without a plan is how two workers land conflicting edits on `docs/PRD.md`
at midnight.

### Briefs, and why they fail

A worker has none of your context. Everything goes in the brief: name every
file it may create and add "and nothing else", give the output format
concretely (headings, table columns, casing), carry the house rules in (80
character wrap, Title Case headings, no emoji, a table must earn itself), and
say that "no change" is a valid outcome. Demand that every factual claim names
the file or command it came from.

### Verification is not optional

**Devin exits 0 when it has done nothing.** Check, every time:

```shell
ls -la <expected outputs>
git status --porcelain                          # strays, including in source repos
grep -c "rejected a tool call\|ignoring --permission-mode" "<log>"
grep -rn "/home/\|/tmp/" <output>               # machine paths must not leak
```

Then read the parts that carry risk and diff them against the source of truth,
not against your expectations. In this session three of five workers produced
exactly correct figures and one fabricated a Move test count (claimed 98,
actual 105) that survived a read-through and was caught only by re-running the
`grep`. Spot-check anything a decision will rest on.

### Issue 4 — kymil4

Title: `Spike field provenance across all four attachment formats`

> This is the gating technical unknown for our whole differentiation strategy.
> The plan is that a judge clicks an extracted value and sees exactly where in
> the source document it was read from, so correctness is checked by eye
> rather than trusted. If that is not achievable per format, the strategy
> changes and we need to know tomorrow, not next week.
>
> ### What to find out, per format
>
> The bundle at `data/sdoc-hackathon-bundle/attachments/` holds 192 `.txt`, 28
> `.pdf`, 22 `.xlsx` and 8 `.docx`. For each, establish what location
> information we can actually recover and surface:
>
> - `.txt` — character offset or line number. Should be trivial; confirm.
> - `.pdf` with a text layer — can we get a bounding box? Which library, and
>   does it survive the layouts in the bundle?
> - `.pdf` that is image-only or scanned — does OCR give us coordinates, and
>   at what quality? Does a vision model return usable regions, or only text?
> - `.docx` — there is no page geometry. What is the best available anchor,
>   for example a table cell reference?
> - `.xlsx` — a cell reference should be exact. Confirm, including merged
>   cells.
>
> Also check: do any of the 8 `.docx` files and 51 `.txt` files with Chinese
> labels behave differently?
>
> ### Done looks like
>
> A short spike, thrown away afterwards, plus a written answer in
> `docs/research/ideation/provenance-spike.md`: a table of format against what
> we can anchor, the library or method for each, and a plain recommendation
> for what the UI is allowed to promise. **"We cannot do it for format X" is a
> valid and useful result.**
>
> ### Why it matters
>
> It decides whether extraction stores a bare value or a value plus a
> location, which is a schema decision we cannot cheaply reverse later.

### Issue 5 — kymil4

Title: `Measure the live-path latency budget`

> The 4th-place entry's pitch script forbade submitting anything on stage,
> because a real check submitted at 16:42 UTC was still queued 25 minutes
> later. That single constraint cost them the demo. We need to know whether we
> can avoid it, with measurements rather than hope.
>
> The target: **a judge hands us an SI and a BL we have never seen, and sees a
> verdict in the room.**
>
> ### What to measure
>
> Use the worst realistic input, not the easiest — a scanned or image-only PDF
> for both documents, ideally with Chinese labels.
>
> - Wall-clock time for extraction of one document with
>   `gemini-3.5-flash-lite`, and whether both documents can go in one call.
> - Time for the comparison and decision step.
> - End-to-end p50 and p95 over at least ten runs.
> - Failure behaviour on a rate limit. The free tier allows 500 requests a day
>   on flash-lite, and `GEMINI_API_KEY_2` only engages on HTTP 429.
>
> ### Done looks like
>
> Measured numbers in `docs/research/ideation/latency.md`, and a yes or no on
> whether a live unseen-document demo is viable. If no, say what would make it
> viable — a smaller model, parallel calls, a narrower first pass — and what
> we should precompute and cache instead.
>
> ### Related
>
> Extraction results should be persisted rather than recomputed on every demo
> run; the daily quota will not survive rehearsals otherwise.
